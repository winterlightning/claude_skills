Disapproved icons, who is fixing them, and what changed

Every icon on production that is disapproved, claimed, or was just fixed and awaits review, read straight from the production database. A claim is simply the review status Claimed with a worker name and time; a claim older than six hours goes back to Disapproved on its own. Open History on a row to compare the drawing the reviewer saw with the current one and to read the full log of reviews, feedback and fix reports. Claims are made by agents with work_queue.py; this page only shows them.

How to fetch, claim and finish a fix

Every machine uses the same production database, so the flow is the same everywhere: fetch the disapproved icons, claim one under your own worker name, fix it, mark it done, then check the result here. Type your worker name above (for example thuan-mac or mac-mini) and the examples below use it. The name is required on every machine: pass --worker or export PICTOGRAPHIC_WORKER=…; the scripts refuse to claim without one, and there is no default. No login is needed; only the same worker name can finish a claim it started, and a claim older than six hours is open to anyone again.

Always the production server: claims live in its database. A local dev server forwards /api/work… calls there, but agents should call production directly.

  1. 1 · Fetch the disapproved icons

    disapproved lists every icon whose review status is Disapproved or Claimed with its work state; queue is the subset you may claim now (open). Filters: family, category, type, limit 1–500, offset; page with next_offset.

    work.stateMeaningClaimable
    opennobody is on ityes
    claimedreview status Claimed: another worker holds it (work.worker, work.expires_at); after six hours it is Disapproved and open againno
    donefixed, back to Ready, waiting for the reviewerno
    cannot-fixDisapproved, but a worker gave up (work.worker, work.note); a reviewer decision or abandon reopens itno

  2. 2 · Claim it

    Send the svg_sha256 the fetch gave you. Production sets the review status to Claimed under your worker name in one conditional update, so two machines can never both win. The answer is 201 with work.state = claimed; six hours after claimed_at the icon is Disapproved and open again, with no heartbeat to send. Upload the current drawing as the before result (step 4) if you want the before/after view.

    Several at once, each accepted or refused on its own (a bare key uses the current hash):

    Refusals: 409 … is working on this icon → take the next one · 409 Icon changed on production → re-fetch and use the returned svg_sha256 · 409 Restore this rejected icon → skip.

  3. 3 · Fix it and build only that icon

    Author the repair as a new variant and validate it. Then build and publish only the icon you fixed; never run a full library build for one fix:

    The per-icon build writes that icon's SVG, manifest row, metadata and gallery entry into published/; publish --no-build only compacts the catalogs and writes release.json. Commit the Python source with the touched files under published/, push, and production gets the new drawing on its next pull. Finish within six hours of the claim; after that the icon is open to other machines again.

  4. 4 · Upload the result, then mark it done

    Before reporting, upload the fixed drawing (and the module and validation text) so this page can show the fix next to the before drawing at once. The same call with stage: before stores the first version; primitive_fix.py start does that for you.

    Production sets this revision back to Ready under your worker name and keeps the disapproval feedback so the reviewer can compare. The icon leaves the queue until a reviewer disapproves it again.

    Other endings: POST /api/work/cannot-fix with a required note, or POST /api/work/abandon to set it back to Disapproved for the queue. Cannot fix is not a review status: the icon stays Disapproved with your worker name and note, and the queue skips it until a reviewer decides again.

  5. 5 · See the result

    The row on this page shows Done · back to Ready until the reviewer decides; History shows the before/after drawings, every revision and the change log. The same data over the API:

    Right after done, current.svg_sha256 still equals the claimed hash and current.work.state is done. After the production pull the current hash is new and that revision starts Ready on its own; the old revision stays in History. The reviewer approves it or disapproves it again, which clears the worker and puts it back in the queue as open.

Or let the CLI do it

icon_set/scripts/work_queue.py talks to production directly. next fetches and claims in one go and prints the brief: --limit is how many icons to claim, --offset skips the first claimable ones, --disapprove-status keeps only one disapproval reason (bad-stroke, meaning, manual-fix-request, other).

The /primitive-fix-thuan skill wraps the whole loop for solo icons: /primitive-fix-thuan 5 --worker thuan-mac claims five, keeps each first version, fixes the registered module in place, uploads before/after and reports done.
